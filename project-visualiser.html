Visualiser by Fiercejojo88862

Song-reactive desktop visualiser for Linux. Built 2026. Sole builder.

  • Python
  • JavaScript
  • Canvas
  • Docker
  • PipeWire
  • MPRIS
  • NumPy

What it does

Whatever is playing on my machine, the visualiser reacts to it. It follows the current track over MPRIS, listens to the system audio monitor for the beat, pulls time-synced lyrics, and fetches short clips and GIFs that match the song. Everything runs in a Docker container that starts when I open the app and stops when I close it.

Open it fullscreen and it is a stage: a blurred artwork backdrop, a procedural canvas of orbs and particles, and a clip cut onto the beat, driven by the actual audio and not a fake animation timer.

How the sync works

Three layers share one clock.

  • Reactive. The PipeWire monitor of the output sink is captured with parec, transformed at about 47 frames per second, and split into sub, bass, low-mid, mid, high, and air envelopes with a per-band adaptive floor and ceiling. Bass drives scale, highs drive rotation and blur, mids drive saturation, air drives contrast.
  • Beat grid. A spectral-flux onset envelope feeds an autocorrelation tempo estimate and a phase-locked loop, so cuts land on beats instead of near them. Tempo locks in about three seconds, and onset bursts plus a loudness spike fire drop events that force a cut, a glitch, a hue jump, and a particle burst.
  • Semantic selection. Lyrics and an audio-derived mood (frenetic, energetic, euphoric, melancholic, calm, dreamy, gritty) become search queries. Results are ranked by keyword and mood overlap, damped by a recency penalty so the same three clips do not loop all night, prefetched in the first seconds of a track, and cached by query so repeat moods get faster.

Streamed sources give you no file to analyse, so live tracking is the primary path. While a track plays once, the engine also records the monitor stream and, after the track ends, analyses it offline into a cached per-track beat timeline. The second listen is tighter than the first.

Five layers on screen

  1. A blurred album-art backdrop that tints the whole stage.
  2. A single additive canvas: six band-driven glow orbs, a particle field where every particle owns one log-spaced band from 32 Hz to 16 kHz and is pushed outward by that band, a 64-bar radial ring, an ultra-thin bottom spectrum, expanding beat rings, and a hue that follows the mood.
  3. The clip itself on two crossfading decks, transformed by the audio (scale, rotate, saturation, contrast, hue) and composited with screen.
  4. A post pass with bloom and RGB channel-split chromatic aberration on transients, sampled at a third of the resolution and switched off automatically below roughly 42 frames per second rather than stuttering.
  5. A HUD with the title, artist, mood, BPM, a metronome ring, a scrubbable progress bar, transport buttons, and a rotating vinyl thumbnail. It fades after 12 seconds of no mouse movement, and H hides it outright.

Colour comes from the cover: it is downscaled with ffmpeg to a 32 by 32 raw buffer, quantised in NumPy into a four-colour palette, and the most vivid cluster tints the orbs, ring, progress bar, and glow, falling back to the mood hue when there is no artwork.

Hardest problems

The one that taught me the most was a bare except that hid a total failure. Offline beat timelines used librosa, and on this machine (Python 3.14) the import raises inside the image: numba's JIT cache cannot find a locator for librosa/core/notation.py. Because the builder caught exceptions with a bare handler, it returned "no beats found" forever, which looks exactly like a track with no beats. Nothing crashed and nothing logged. It is now the same NumPy maths as the live tracker, verified at 72, 100, and 128 BPM on synthetic material.

The second was letterboxing that lives inside the file. Provider memes are often padded into a square or 4:3 frame, a 640 by 480 file carrying 640 by 360 of picture, so object-fit: cover still leaked black bars whenever the window was not exactly 16:9. Each clip is now measured with cropdetect at import and, when bars are found, transcoded once to a cropped *.fit.webm with dark scenes rejected so the detector cannot collapse, and the decision memoised next to the clip.

A smaller one: moving the folder used to break startup with a bare "Directory not found", because the installed systemd unit still pointed at the old path. The installer now renders the unit and desktop entry with the checkout's real path, and the launcher repairs a stale unit on its own.

Container as a reproducibility wrapper

The image is Arch-based on purpose, so mesa, Qt, and ffmpeg inside it match the host's GPU stack. The container needs the host's Wayland socket, PipeWire socket, session bus, and render node, so it is not a sandbox; it is a way to pin a 3.2 GB toolchain that I can rebuild the same way. It runs as my uid, uses NumPy only (no librosa, numba, or scipy), and the systemd user unit treats the container process as the service, so closing the window really does stop everything.

Privacy and limits

Tenor shut down its public API on 30 June 2026, so the provider is KLIPY, built by the ex-Tenor engineers, with GIPHY as a paid fallback. Both forbid re-hosting their media, so the clip cache is local playback only, capped and evicted least-recently-used at 6 GB. The offline analysis records the system monitor, analyses it, then deletes the wav, and that recording can be turned off entirely. The renderer keeps its "Powered by KLIPY" attribution on screen.

Outcome

It is the thing I open when I want music to look like something. When the provider is unconfigured, rate limited, or offline, the procedural layer keeps running instead of going black, so the visual never depends on a network call. My own GIF folder works with no API key at all, and new files are picked up while it runs.
